## どの経歴書も、同じに見える

業務システムの開発会社で働く鈴木さん（仮名）は、転職を考え始めて、経歴書を書いていました。

> Java（5年）／Spring Boot／PostgreSQL。詳細設計・実装・単体テストを担当。

書き終えてから、ほかの人の経歴書の例を眺めると、ほとんど同じ言葉が並んでいました。鈴木さんには、自分なりに大事にしてきた仕事の仕方があります。変更を入れるときは、テストも一緒に直す。小さく変えて、すぐ確かめる。けれど、それを経歴書に書くと「丁寧に仕事をします」という言葉にしかなりません。

## 書けないのは、仕事の中身ではなく「証拠」

鈴木さんの仕事の大半は、会社の非公開リポジトリの中にあります。社外に持ち出せるものではありません。一方で、数年前から続けている個人の公開リポジトリがありました。家計簿アプリのAPIを、少しずつ直してきたものです。

「ここなら、自分の仕事の仕方が残っているかもしれない」。鈴木さんは、そのリポジトリでGrift CLIを実行しました。

```bash
pipx install grift-cli
cd household-api
grift report
```

## 記録を読む

保存されたレポート（`.grift/report.md`）には、こんな記録が並んでいました（数値は説明のための例です）。

- 本番コードを変えたコミット212件のうち、71件で同じコミットのテストも変更（test co-change 0.33、71 of 212）
- 同じファイルを短い間隔で触り直した割合や、fix・revertでやり直した割合（どちらも傾向の「観測」で、良し悪しの判定ではない）
- 依存関係を更新するbotのコミットは、鈴木さんの仕事とは別に数えられていた

自分では「いつもテストを直している」と思っていましたが、記録では3回に1回ほどでした。思っていたのとは違いました。それでも鈴木さんは、むしろ書きやすくなったと感じました。盛らずに書ける、確かめられる数字だからです。

## 経歴書に1行を書き足す

鈴木さんは、経歴書にこう書き足しました。

> 個人の公開リポジトリ（household-api）で、本番コードを変えた212件のうち71件は、同じコミットでテストも変更しています（Grift CLIで計測。grift verifyで再計算できます）。業務のリポジトリは非公開のため、含めていません。

最後の一文が大事です。Griftの利用規範（norms）は、記録が無いことを「実績が無い」と読まないこと、そしてどのリポジトリを選んで見せているのかを明示することを求めています。公開リポジトリだけを選んで見せていると書いておけば、読む側も誤解しません。

## この物語で伝えたいこと

- 年数や担当工程に、受け取った側が確かめられる事実を1行添えるだけで、仕事の仕方が伝わりやすくなります
- 数字は盛れません。だからこそ、思っていたのと違っても、そのまま書けます
- 非公開の仕事が見えないのは当然です。見せる範囲を自分で選び、選んだことも書いておきましょう
